# TeamFlow

اپلیکیشن مدیریت پروژه و تیم — ساخته‌شده با Next.js 15 (App Router)، Mongoose (MongoDB)، NextAuth و Material UI (MUI).

## امکانات
- احراز هویت کاربر (ثبت‌نام و ورود با ایمیل/رمز عبور، NextAuth + bcrypt)
- **تیم و مدیر تیم**: هر کاربری که تیم بسازه، مدیر همون تیمه و می‌تونه عضو اضافه/حذف کنه
- **مدیر پروژه**: مدیر یک تیم می‌تونه چند پروژه برای همون تیم بسازه؛ هر پروژه فقط به یک تیم تعلق داره
- **ایزوله بودن دسترسی بین تیم‌ها**: تیم‌های دیگه پروژه رو اصلاً نمی‌بینن
- **دسترسی پروژه‌محور، نه تیم‌محور**: عضویت در تیم به‌تنهایی دسترسی به همهٔ پروژه‌های اون تیم
  نمی‌ده — مدیر پروژه (که همون مدیر تیمه) از یه دیالوگ اختصاصی، تک‌تک اعضای تیم رو به هر پروژه
  اضافه یا ازش حذف می‌کنه؛ این کنترل روی بک‌اند اجرا می‌شه، نه فقط توی UI
- بورد کانبان با Drag & Drop بین **ستون‌های کاملاً دلخواه** — نه سه وضعیت ثابت؛ هر تیم می‌تونه
  هر تعداد ستون با هر اسمی بسازه، تغییر نام بده، یا حذف کنه (تا وقتی خالی باشه)، و یکی از
  ستون‌ها رو به‌عنوان «ستون پایانی» علامت بزنه که مبنای محاسبهٔ درصد پیشرفت می‌شه
- **جابه‌جایی دقیق تسک‌ها**: نه فقط بین ستون‌ها، بلکه *داخل* یک ستون هم می‌تونی تسک رو دقیقاً
  بالا یا پایین یه تسک دیگه رها کنی — یه خط راهنما نشون می‌ده کجا قرار می‌گیره
- **تسک‌های چند-مسئولی** (مثل ترلو): هر تسک می‌تونه به یک یا چند نفر از اعضای تیم واگذار بشه
- **پیوست فایل روی تسک**: آپلود، دانلود و حذف فایل برای هر تسک — حداکثر ۵ مگابایت هر فایل،
  حداکثر ۸ مگابایت مجموع پیوست‌های هر تسک، و حداکثر ۲۰ فایل روی هر تسک
- **تأیید قبل از حذف**: حذف تسک، ستون، عضو تیم، و پروژه همه یه دیالوگ تأیید دارن — هیچ‌کدوم
  مستقیم و بدون هشدار حذف نمی‌شن
- **حساب کاربری و تیم**: از صفحهٔ «Account» (روی نام شما در نوبار) می‌تونی اسمت رو عوض کنی، رمز عبور رو
  با وارد کردن رمز فعلی تغییر بدی (همهٔ نشست‌ها بسته می‌شن) و حسابت رو حذف کنی. مدیر تیم می‌تونه تیم رو
  (با تایپ نامش) حذف کنه؛ اعضا می‌تونن تیم رو ترک کنن. مدیر تیم نمی‌تونه تیم رو ترک کنه و تا وقتی مدیر
  تیمی هست نمی‌تونه حسابش رو حذف کنه — چون انتقال مالکیت وجود نداره، اول باید تیم حذف بشه
- **دعوت با ایمیل برای افرادی که هنوز حساب ندارن**: اگه ایمیلی رو به تیم دعوت کنی که هنوز
  توی برنامه ثبت‌نام نکرده، یه ایمیل دعوت براش می‌ره؛ همین که با همون ایمیل ثبت‌نام کنه،
  خودکار به اون تیم(ها) اضافه می‌شه — بدون این‌که مدیر تیم لازم باشه دوباره کاری کنه
- **تأیید ایمیل با JWT**: بعد از ثبت‌نام، یه ایمیل تأیید (با لینک حاوی JWT، اعتبار ۲۴ ساعته)
  فرستاده می‌شه. تا وقتی کاربر روی لینک کلیک نکنه و ایمیلش تأیید نشه، اجازهٔ ورود نداره —
  از صفحهٔ ورود هم می‌شه دوباره ایمیل تأیید رو فرستاد (Resend)
- **حالت روشن/تاریک**: پیش‌فرض از تنظیمات سیستم کاربر می‌گیره (`prefers-color-scheme`)، ولی
  از دکمهٔ آفتاب/ماه توی نوبار می‌شه دستی عوضش کرد — انتخاب دستی توی مرورگر ذخیره می‌مونه
- **رنگ‌های پاستلی**: هر تسک می‌تونه یکی از ۸ رنگ پاستلی رو به‌عنوان لیبل بگیره (از دیالوگ
  جزئیات تسک یا موقع ساختنش)؛ آواتار افراد و بج تیم هم بر اساس شناسه‌شون یه رنگ پاستلی ثابت
  می‌گیرن، که هرکسی همیشه همون رنگ رو داره. توی حالت تاریک، همین رنگ‌ها به نسخهٔ تیره و
  کم‌رنگ‌شدهٔ خودشون تبدیل می‌شن، نه اینکه روشن و پرزرق‌وبرق بمونن
- **پالت خنثی و گرم، بدون گرادیان**: کل رنگ‌بندی برنامه (نه فقط لیبل تسک‌ها) روی یک پس‌زمینهٔ
  خنثی و یک لهجهٔ اُکِری solid بنا شده — بدون گرادیان، گلس‌مورفیسم یا سایه‌های تزئینی؛
  دکمه‌های اصلی (Sign in، Create project و…) پس‌زمینهٔ تخت دارن، نه گرادیانی. فونت بدنه
  Plus Jakarta Sans (کنار Fraunces برای تیترها) که شخصیت بیشتری داره ولی همچنان خوانا و مرتبه
- داشبورد با گزارش پیشرفت هر پروژه (نمودار با Recharts) و آمار کلیک‌پذیر (کلیک روی هر عدد،
  لیست مربوطه رو زیرش باز می‌کنه)

## راه‌اندازی محلی

```bash
# ۱. نصب پکیج‌ها
npm install

# ۲. تنظیم متغیرهای محیطی
cp .env.example .env
```

مقدار `MONGODB_URI` رو با connection string واقعی MongoDB Atlas خودت پر کن:
1. توی داشبورد Atlas برو به Database → Connect → Drivers
2. رشتهٔ اتصال رو کپی کن (چیزی شبیه `mongodb+srv://user:pass@cluster0.xxxxx.mongodb.net/`)
3. اسم دیتابیس (مثلاً `teamflow`) رو قبل از `?retryWrites=...` اضافه کن
4. توی Atlas، از بخش Network Access مطمئن شو IP فعلیت (یا `0.0.0.0/0` برای تست) مجاز باشه

مقدار `NEXTAUTH_SECRET` رو هم با این دستور بساز:
```bash
openssl rand -base64 32
```

**متغیرهای ایمیل (برای تأیید ایمیل و دعوت با ایمیل):**
دو فیچر بهشون نیاز دارن: تأیید ایمیل بعد از ثبت‌نام (اجباریه برای ورود)، و دعوت با ایمیل
برای افرادی که هنوز حساب ندارن. برای اینکه واقعاً ایمیل بفرستن، `EMAIL_SERVER_HOST` و بقیهٔ
متغیرهای ایمیل رو توی `.env` (کپیِ `.env.example`) از حالت کامنت دربیار و پر کن — هر SMTP‌ای کار می‌کنه (Gmail با App Password،
Mailtrap رایگان برای تست، SendGrid/Resend و…).

اگه پرشون نکنی، برنامه خطا نمی‌ده — به‌جای فرستادن ایمیل واقعی، **کل متن ایمیل (همراه با
لینک تأیید/دعوت) رو توی کنسول سرور (ترمینالی که `npm run dev` توش اجرا شده) چاپ می‌کنه**،
پس موقع تست محلی می‌تونی لینک رو از همون‌جا کپی کنی و دستی باز کنی — لازم نیست حتماً SMTP
واقعی وصل کنی تا بتونی تست کنی.

سپس اجرا کن:
```bash
npm run dev
```

نیازی به migration نیست — Mongoose مستقیم به Atlas وصل می‌شه و کالکشن‌ها با اولین insert
خودشون ساخته می‌شن. بعد به آدرس `http://localhost:3000` برو.

**نکتهٔ مهم دربارهٔ تراکنش‌های MongoDB:** چند عملیات حساس (ساخت پروژه به‌همراه ستون‌های
پیش‌فرضش، حذف پروژه، حذف عضو تیم، ثبت‌نام با مصرف دعوت‌نامه، و رعایت قانون «فقط یک ستون
پایانی») داخل تراکنش واقعی Mongo
(`session.withTransaction`) انجام می‌شن. تراکنش فقط روی یک **replica set** کار می‌کنه —
یک Atlas cluster همیشه replica set هست، پس روی Atlas مشکلی نیست. اگه به‌جاش یک `mongod`
standalone محلی وصل بشی، این عملیات‌ها به‌جای شکست خوردن، به‌صورت خودکار بدون تراکنش
(بدون هیچ ایزولیشنی بین دو درخواست هم‌زمان) اجرا می‌شن — کافیه برای توسعهٔ تک‌نفره، ولی برای
تست واقعی رفتار همزمانی حتماً باید در برابر یک replica set واقعی (مثلاً همون Atlas) تست بشه.

## جریان کار (Workflow)

1. ثبت‌نام کن — یه ایمیل تأیید برات میاد؛ روی لینکش بزن، بعد وارد شو.
2. از صفحهٔ «تیم‌ها» یک تیم بساز — خودت به‌طور خودکار مدیر همون تیم می‌شی.
3. با ایمیل، همکارهاتو به تیم دعوت کن.
4. از صفحهٔ «پروژه‌ها»، یک پروژهٔ جدید بساز و تیم موردنظر رو انتخاب کن — سه ستون پیش‌فرض
   (برای انجام / در حال انجام / انجام‌شده) خودکار ساخته می‌شن، ولی می‌تونی هر تعداد ستون
   دیگه هم اضافه کنی، اسمشونو عوض کنی، یا حذفشون کنی.
5. توی پروژه، تسک بساز و به یک یا چند نفر از اعضای تیم واگذارش کن.
6. روی هر تسک کلیک کن تا جزئیاتش (مسئول‌ها، فایل‌های پیوست) باز بشه.

## آمار پروژه (به‌روز شده در فاز Next.js 15)

- **صفحات (App Router pages):** ۹ صفحه — `/`، `/login`، `/register`، `/verify-email`،
  `/dashboard`، `/dashboard/projects`، `/dashboard/projects/[id]`، `/dashboard/teams`،
  `/dashboard/teams/[id]`
- **API Route handlers:** ۱۶ فایل `route.js` زیر `src/app/api/`، جمعاً ۲۲ متد HTTP
  (GET/POST/PATCH/DELETE) — auth (۴ فایل)، teams (۴ فایل)، projects (۴ فایل)، tasks (۴ فایل)

## احراز هویت (Authentication Flow)

1. ثبت‌نام با ایمیل/رمز عبور (`POST /api/auth/register`) — رمز با bcrypt هش می‌شه و یک
   ایمیل تأیید حاوی JWT (اعتبار ۲۴ ساعته) فرستاده می‌شه.
2. ورود از طریق NextAuth v4 با `CredentialsProvider` (استراتژی session از نوع JWT، نه
   دیتابیس) — تا وقتی ایمیل کاربر تأیید نشده باشه، `authorize()` با خطای
   `EmailNotVerified` ورود رو رد می‌کنه.
3. تأیید ایمیل از طریق `GET/POST /api/auth/verify-email` با توکن JWT همون لینک؛ در صورت
   نیاز، `POST /api/auth/resend-verification` یک ایمیل تأیید تازه می‌فرسته.
4. بعد از ورود، `session.user.id` (از JWT callback) مبنای همهٔ چک‌های دسترسی
   (`lib/authz.js`) روی تیم‌ها، پروژه‌ها و تسک‌هاست.

## ساختار پروژه

```
src/
  app/
    api/            ← API Routes (auth, teams, projects, tasks, attachments)
    dashboard/       ← صفحات محافظت‌شده (داشبورد، تیم‌ها، پروژه‌ها، بورد کانبان)
    login/ register/ ← صفحات احراز هویت
  components/        ← Navbar, KanbanBoard, TaskCard, TaskDetailDialog, ProgressChart, ThemeRegistry, ...
  models/             ← اسکیمای Mongoose (User, Team, Project, Column, Task, Invitation)
  lib/                ← اتصال Mongoose، تنظیمات NextAuth، تبدیل به DTO، تم MUI، ارسال ایمیل (email.js)
```

## مدل داده (Mongoose)

- **User** — کاربران (نام، ایمیل، هش رمز عبور)
- **Team** — تیم‌ها؛ هر تیم یک `manager` (کاربری که تیم رو ساخته) و آرایه‌ای از `members` داره
- **Project** — پروژه‌ها؛ هر پروژه دقیقاً به یک `team` تعلق داره و یک `manager` (سازنده‌ش) داره،
  و یک آرایهٔ `members` که مشخص می‌کنه دقیقاً کدوم اعضای تیم بهش دسترسی دارن (پایین‌تر توضیح
  داده شده)
- **Column** — ستون‌های بورد؛ کاملاً دلخواه (نه enum ثابت). هر ستون یک `name`، `order`، و
  فلگ `isDoneColumn` داره — همون فلگیه که تعیین می‌کنه تسک‌های اون ستون توی گزارش پیشرفت
  «انجام‌شده» حساب بشن یا نه. هر پروژه با سه ستون پیش‌فرض شروع می‌شه ولی تیم می‌تونه هر
  تعداد ستون دیگه اضافه/حذف/تغییر نام بده.
- **Task** — تسک‌ها؛ رفرنس به `project` و `column` (نه یک وضعیت ثابت)، آرایهٔ `assignees`
  (چند کاربر)، و آرایهٔ `attachments` (فایل‌های پیوست به‌صورت base64 مستقیم داخل خودِ سند
  تسک ذخیره می‌شن)
- **Invitation** — دعوت‌های در انتظار؛ وقتی مدیر تیم ایمیلی رو دعوت می‌کنه که هنوز حساب
  نداره، یه رکورد اینجا ساخته می‌شه (`email`, `team`, `invitedBy`). به‌محض این‌که اون فرد
  با همون ایمیل ثبت‌نام کنه، رکورد مصرف می‌شه و خودکار عضو تیم می‌شه.

**کنترل دسترسی:** عضو بودن در یک تیم به‌تنهایی دسترسی به همهٔ پروژه‌های اون تیم رو نمی‌ده. هر
پروژه یک `manager` (که همیشه دسترسی داره) و یک لیست `members` داره — فقط این دو دسته می‌تونن
پروژه رو باز کنن، بوردش رو ببینن، یا به تسک‌هاش دسترسی داشته باشن. فقط مدیر پروژه (که همون مدیر
تیمه، چون فقط مدیر تیم می‌تونه پروژه بسازه) می‌تونه از دیالوگ «Manage access» روی صفحهٔ پروژه،
تک‌تک اعضای تیم رو به پروژه اضافه یا ازش حذف کنه؛ کسی که عضو تیم نیست اصلاً قابل‌اضافه‌شدن نیست.
این چک توی همهٔ API Routeهای مربوط به پروژه، ستون، تسک و پیوست انجام می‌شه (روی بک‌اند، نه فقط
مخفی‌کردن دکمه‌ها توی UI) — یعنی حتی با درخواست مستقیم به API هم نمی‌شه به پروژه‌ای که بهت اضافه
نشدی دسترسی پیدا کرد.

پروژه‌هایی که قبل از این قابلیت ساخته شدن (یعنی هنوز فیلد `members` رو ندارن) طبق رفتار قبلی کار
می‌کنن — همهٔ اعضای تیم بهشون دسترسی دارن — تا وقتی مدیرشون برای اولین بار از همون دیالوگ کسی رو
اضافه یا حذف کنه؛ در اون لحظه پروژه با لیست فعلی اعضای تیم seed می‌شه (تا کسی دسترسیش رو از دست
نده) و از اون به بعد محدود می‌شه.

**دربارهٔ پیوست فایل:** فایل‌ها به‌صورت base64 داخل خودِ سند MongoDB ذخیره می‌شن — راه‌حلی ساده
که نیازی به سرویس ذخیره‌سازی جدا (مثل S3) نداره. محدودیت‌های فعلی (در `src/lib/attachmentPolicy.js`
تعریف شده و همون چیزیه که سرور واقعاً اعمال می‌کنه):

| محدودیت | مقدار |
| --- | --- |
| حجم هر فایل | ۴ مگابایت (MiB) |
| مجموع فایل‌های پیوست‌شده در لحظهٔ ساخت تسک (یک درخواست) | ۴ مگابایت |
| مجموع فایل‌های یک تسک (روی هم، با آپلودهای بعدی) | ۸ مگابایت |
| تعداد فایل در هر تسک | ۲۰ |

حجم‌ها بر اساس **بایت‌های خام فایل** حساب می‌شن، نه base64: فایل‌ها به‌صورت باینری (multipart) آپلود
و به‌صورت باینری دانلود می‌شن؛ base64 فقط روی چیزیه که توی MongoDB ذخیره می‌شه (برای همین سقف ۸
مگابایتیِ هر تسک، که بعد از encode حدود ۱۰٫۷ مگابایت می‌شه و زیر سقف ۱۶ مگابایتیِ سند MongoDB
می‌مونه).

**چرا ۴ مگابایت؟** Vercel برای درخواست و پاسخ هر Function سقف ۴٫۵ مگابایت می‌ذاره و درخواست
بزرگ‌تر رو خودش (قبل از رسیدن به کد اپ) با خطای 413 `FUNCTION_PAYLOAD_TOO_LARGE` رد می‌کنه؛
پاسخ بزرگ‌تر از اون هم (مگر stream بشه) خطای 500 می‌ده. بدنهٔ یک آپلود، علاوه بر فایل، مرزها و
هدرهای multipart رو هم داره (کمتر از ۱ کیلوبایت برای یک فایل؛ کد تا ۶۴ کیلوبایت برای این سربار
بودجه می‌ذاره)، و درخواست ساخت تسک JSON خودِ تسک رو هم داره. با سقف ۴ مگابایت، بزرگ‌ترین درخواست
مجاز حدود ۴٫۳ مگابایت می‌شه — یعنی حدود ۲۰۰ کیلوبایت زیر سقف Vercel.
چون مجموعِ فایل‌های هر درخواست ساخت تسک هم به همین دلیل ۴ مگابایت محدود شده، برای فایل‌های
بیشتر باید بعد از ساخت تسک، فایل‌ها رو یکی‌یکی از داخل خودِ تسک اضافه کرد (تا سقف ۸ مگابایتِ تسک).
فایل‌هایی که قبل از این تغییر (با سقف قدیمیِ ۵ مگابایت) ذخیره شدن همچنان معتبر می‌مونن و دانلود
می‌شن؛ اونایی که از ۴ مگابایت بزرگ‌ترن به‌صورت stream برگردونده می‌شن تا به سقف پاسخ نخورن.

**وضعیت تأیید:** این محاسبه و رفتار اپ تو محیط تست خودکار (درخواست‌های multipart واقعی) بررسی شده،
اما **روی دیپلوی واقعی Vercel تست نشده** — پس رفتار خودِ Vercel (مثلاً رد شدن درخواست بالای
۴٫۵ مگابایت یا stream شدن پاسخ‌های بزرگ) هنوز تأییدنشده‌ست و قبل از انتشار باید روی یک
Preview Deployment تست بشه. اگه به فایل‌های بزرگ‌تر نیاز دارید، راه درستش آپلود مستقیم از مرورگر
به یک سرویس ذخیره‌سازی (مثل Vercel Blob یا S3) است، نه بالا بردن این سقف‌ها.

## توسعه، Lint و Build

```bash
npm run lint    # eslint . — چک کیفیت کد
npm run build   # next build — بیلد نهایی برای production
npm run dev     # next dev — سرور توسعه
```

**نکتهٔ دربارهٔ `npm run build`:** بیلد دیگه به `MONGODB_URI` و `NEXTAUTH_SECRET` نیاز نداره
(با env خالی هم کامل می‌شه). این دو مقدار فقط موقع اجرا چک می‌شن: اولین اتصال به
دیتابیس بدون `MONGODB_URI`، و هر کاری که با `NEXTAUTH_SECRET` امضا/تأیید می‌کنه
(ورود، توکن تأیید ایمیل) بدون اون، با پیام خطای واضح شکست می‌خوره. پس روی سرور/Vercel
حتماً هر دو رو ست کن؛ `NEXTAUTH_SECRET` توی `.env.example` عمداً خالیه.
اتصال به MongoDB هم timeout مشخص داره (انتخاب سرور ۵ ثانیه، اتصال ۱۰ ثانیه، عملیات
در حال اجرا ۳۰ ثانیه) تا قطعی دیتابیس درخواست‌ها رو بی‌پایان معطل نکنه.

**نسخهٔ Node.js:** پروژه به Node.js نسخهٔ `^18.18.0`، `^19.8.0`، یا
`>=20.0.0` نیاز داره (همون چیزی که خودِ Next.js 15.5 لازم داره؛ توی
`engines` فیلد `package.json` هم ثبت شده).

`npm run lint` از `eslint` (نسخهٔ ۹، با flat config توی
`eslint.config.mjs`) استفاده می‌کنه — نه `next lint` قدیمی که توی
Next.js 16 کلاً حذف می‌شه.

## دیپلوی روی Vercel

سقف حجم پیوست‌ها طوری تنظیم شده که زیر محدودیت ۴٫۵ مگابایتیِ درخواست/پاسخ Vercel بمونه — جزئیات
و وضعیت تأیید در بخش «دربارهٔ پیوست فایل» بالا.

`MONGODB_URI` و `NEXTAUTH_SECRET` رو توی تنظیمات Environment Variables پروژه در Vercel اضافه
کن، و `NEXTAUTH_URL` رو به آدرس دامنهٔ نهایی (مثلاً `https://team-flow.vercel.app`) تغییر بده.

**دربارهٔ `NEXTAUTH_URL` و ایمیل (M8):** لینک تأیید ایمیل، بازیابی رمز و دعوت از روی `NEXTAUTH_URL` ساخته می‌شه. روی production اگه این مقدار ست نشده باشه، URL معتبر نباشه یا به `localhost` اشاره کنه، ایمیل **فرستاده نمی‌شه** و به‌جاش یک خطای `EMAIL_CONFIG` توی لاگ سرور ثبت می‌شه (خودِ ثبت‌نام/دعوت/درخواست بازیابی همچنان ثبت و با همون پاسخ قبلی جواب داده می‌شه). روی توسعه، مقدار خالی یا نامعتبر به `http://localhost:3000` برمی‌گرده.

**دربارهٔ SMTP (M9):** اتصال SMTP سقف زمانی داره (اتصال/greeting/DNS هرکدوم ۵ ثانیه، سکوت سوکت ۸ ثانیه، و کل ارسال حداکثر ۱۰ ثانیه) تا سرور کند، درخواست رو بی‌پایان معطل نکنه؛ این مقدارها ثابت‌های داخل `src/lib/email.js` هستن. خطاها به‌صورت `EmailError` با کدهای `SMTP_TIMEOUT`، `SMTP_CONNECTION`، `SMTP_AUTH`، `SMTP_REJECTED`، `SMTP_ERROR` لاگ می‌شن (بدون رمز و آدرس گیرنده). ارسال ایمیل بعد از commit شدن دیتابیس انجام می‌شه و شکستش چیزی رو برنمی‌گردونه.

**دربارهٔ محدودیت نرخ بر اساس IP:** برای شناسایی IP واقعی کاربر (برای rate limit
ثبت‌نام، ورود، و دعوت اعضای تیم)، اپ به هدر `x-forwarded-for` اعتماد می‌کنه — چون
Vercel این هدر رو خودش روی edge network بازنویسی می‌کنه و مقدار ارسالی از سمت
کلاینت رو عبور نمی‌ده (یعنی روی دیپلوی مستقیم روی Vercel، این هدر توسط کاربر
قابل جعل نیست). اگه پروژه رو جای دیگه‌ای (سلف‌هاست، پشت یک ریورس‌پروکسی دیگه، یا
بدون هیچ پروکسی‌ای) دیپلوی می‌کنی، باید `RATE_LIMIT_TRUST_PROXY=none` رو ست کنی
مگر اینکه مطمئن باشی پروکسی‌ت این هدر رو برای کلاینت‌های غیرقابل‌اعتماد بازنویسی
می‌کنه، نه صرفاً بهش اضافه می‌کنه. جزئیات کامل توی `src/lib/clientIp.js` و
`.env.example` هست.

**دربارهٔ برد اشتراکی عمومی (H4):** مسیر `GET /api/shared/board/[token]` همیشه محدودیت نرخ داره:
اگه IP قابل‌اعتماد باشه، ۶۰ درخواست در دقیقه برای هر IP؛ اگه IP قابل تشخیص نباشه (مثلاً
`RATE_LIMIT_TRUST_PROXY=none`)، همهٔ درخواست‌ها توی **یک** سطل مشترک (`shared-board:no-ip-fallback`،
۶۰۰ در دقیقه) شمرده می‌شن. کلید این سطل ثابته و از هدرهای درخواست ساخته نمی‌شه، پس نه جعل هدر
می‌تونه سطل جدید بسازه و نه دیتابیس بزرگ می‌شه؛ همون TTL بقیهٔ محدودکننده‌ها (`expiresAt`) رو داره.
هزینه‌اش اینه که وقتی IP واقعی ناشناخته‌ست، یک کلاینت بدرفتار می‌تونه سطل مشترک رو پر کنه و بقیه تا
پایان پنجره (پاسخ ۴۲۹ با `Retry-After`) صبر کنن. اگه خودِ محدودکننده کار نکنه (قطعی دیتابیس)، این مسیر
**fail-closed** هست: پاسخ ۵۰۳ با `Retry-After`، نه عبور بدون محدودیت. (مسیرهای ورود/ثبت‌نام/بازیابی
رمز همچنان رفتار قبلی fail-open رو دارن؛ فقط این مسیر `failClosed: true` می‌خواد.)

پاسخ این مسیر هم محدوده (`src/lib/sharedBoardLimits.js`): حداکثر ۵۰ ستون، ۵۰۰ تسک، ۱۰ مسئول برای هر
تسک (`assigneeCount` تعداد واقعی رو نگه می‌داره)، ۲۰ پیوست (فقط نام/نوع/حجم)، توضیحات ۲۸۰ کاراکتر
(کارت فقط دو خط رو نشون می‌ده) و سقف ۳٬۰۰۰٬۰۰۰ بایت برای لیست تسک‌ها (زیر حد ~۴٫۵MB پلتفرم). اگه برد
بزرگ‌تر باشه چیزی بی‌صدا حذف نمی‌شه: `limits.truncated` و تعداد کل/نمایش‌داده‌شده توی پاسخ هست، هر ستون
`taskCount` واقعی خودش رو داره، پیشرفت (progress) برای کل برد حساب می‌شه، و صفحه یک اطلاعیه نشون می‌ده.
برش قطعی‌ه: ستون‌ها به ترتیب برد، تسک‌ها به ترتیب `(order, createdAt, _id)` — یعنی هر ستون اولین
تسک‌هاش رو نشون می‌ده. لینک‌های اشتراکی تاریخ انقضا ندارن (فقط غیرفعال/بازتولید که به ۴۰۴ می‌رسه).

## سازگاری با Next.js 15

پروژه از Next.js 15.5.25 استفاده می‌کنه، جایی که `params` توی هر Route Handler و صفحهٔ
داینامیک به‌صورت یک `Promise` پاس داده می‌شه (نه یک آبجکت معمولی مثل Next.js 14) و باید
`await` بشه — مثلاً:

```js
export async function GET(req, { params }) {
  const { id } = await params;
  // ...
}
```

همهٔ Route Handlerهای داینامیک زیر `src/app/api/` (تیم‌ها، پروژه‌ها، تسک‌ها، پیوست‌ها،
دعوت‌نامه‌ها) از همین الگو پیروی می‌کنن. صفحات داینامیک سمت کلاینت
(`dashboard/projects/[id]`, `dashboard/teams/[id]`) از هوک `useParams()` استفاده می‌کنن که
این تغییر روش شامل حالش نمی‌شه.

## وصله‌های امنیتی سطح Medium (M1–M6)

- **M1 – پیش‌ربایی حساب (pre-hijacking):** هنگام ثبت‌نام یک کوکی `tf_reg_bind` (HttpOnly، SameSite=Strict، فقط روی `/api/auth`) روی همان مرورگر ست می‌شود و توکن ایمیل فقط هش آن را دارد. اگر لینک تأیید در **همان مرورگر** باز شود، رفتار قبلی (تأیید + ورود خودکار) حفظ می‌شود. اگر در مرورگر/دستگاه دیگری باز شود، ایمیل تأیید می‌شود ولی رمزی که روی حساب بود **در همان نوشتن اتمیک دور ریخته می‌شود**، ورود خودکار صادر نمی‌شود و کاربر با همان توکن یک‌بارمصرف بازنشانی رمز، رمز خودش را انتخاب می‌کند (`/reset-password?from=verification`).
- **M2 – ابطال نشست‌ها:** بازنشانی رمز `User.tokenVersion` را زیاد می‌کند؛ callback مربوط به `jwt` در `lib/auth.js` در هر درخواست نسخهٔ داخل JWT را با دیتابیس مقایسه می‌کند. توکن‌های بدون مهر نسخه (قبل از این وصله) رد می‌شوند، یعنی بعد از دیپلوی همه یک‌بار دوباره وارد می‌شوند.
- **H1 – کش کوتاه‌مدت بررسی نشست:** برای جلوگیری از یک `User.findById` در هر درخواست، `tokenVersion` و نام کاربر در یک کش درون‌پردازه‌ای (`lib/sessionRevocationCache.js`، حداکثر ۱۰ ثانیه و ۱۰۰۰ ورودی) نگه داشته می‌شود. در همان پردازه‌ای که رمز را تغییر می‌دهد/بازنشانی می‌کند، نام را عوض می‌کند یا حساب را حذف می‌کند، ورودی بلافاصله پاک می‌شود؛ در پردازه‌های دیگر (مثلاً نمونه‌های جدا در Vercel) توکن ابطال‌شده حداکثر تا ۱۰ ثانیه ممکن است هنوز پذیرفته شود. خطای دیتابیس همچنان نشست را رد می‌کند (fail closed).
- **M3 – قفل‌کردن حساب دیگران:** سه شمارنده به ترتیب: IP (۳۰ تلاش/۱۵ دقیقه)، ایمیل+IP (۱۰ تلاش ناموفق/۱۵ دقیقه، با ورود موفق صفر می‌شود)، و ایمیل به‌تنهایی به‌عنوان پشتیبان با آستانهٔ بالا (۵۰). درخواستی که در مرحلهٔ قبل رد شود شمارندهٔ بعدی را افزایش نمی‌دهد. اگر `RATE_LIMIT_TRUST_PROXY=none` باشد (IP قابل تشخیص نیست) همان محدودیت قدیمی فقط-ایمیل (۱۰) اعمال می‌شود. «فراموشی رمز» هیچ‌وقت توسط این محدودکننده بلاک نمی‌شود.
- **M4 – افزودن عضو:** `POST /api/teams/[id]/members` همیشه فقط **دعوت** می‌سازد و برای ایمیل دارای حساب و بدون حساب پاسخ یکسان (`{status:"invited"}`) می‌دهد. کاربر موجود از بخش «Invitations» صفحهٔ Teams (`/api/invitations`) دعوت را قبول یا رد می‌کند. ثبت‌نام با ایمیل دعوت‌شده مثل قبل خودکار عضو می‌کند.
- **M5 – رمز عبور:** سیاست واحد در `lib/passwordPolicy.js` (حداقل ۶ نویسه، حداکثر ۷۲ **بایت** UTF-8) برای ثبت‌نام، بازنشانی و کلاینت. هیچ‌چیز بی‌صدا بریده نمی‌شود. **توجه:** حساب‌های قدیمی که رمزی بیش از ۷۲ بایت (ولی ≤۷۲ واحد UTF-16، مثلاً متن CJK بلند) داشتند دیگر با رمز کامل وارد نمی‌شوند و باید از «فراموشی رمز» استفاده کنند.
- **M6 – هدرهای امنیتی:** `next.config.js` (nosniff، X-Frame-Options، Referrer-Policy، Permissions-Policy، HSTS فقط در production) و `src/middleware.js` (CSP با nonce برای هر درخواست). به‌خاطر nonce همهٔ صفحات per-request رندر می‌شوند. برای مشاهدهٔ بدون بلاک‌کردن می‌توان `CSP_REPORT_ONLY=1` گذاشت. HSTS شامل `includeSubDomains` است و `preload` ندارد.

## نکاتی برای دفاع از پروژه

- **معماری**: Next.js App Router با Server Components برای صفحات فقط-خواندنی (داشبورد) و
  Client Components برای بخش‌های تعاملی (بورد کانبان، فرم‌ها).
- **امنیت**: رمزهای عبور با bcrypt هش می‌شن؛ هر API Route قبل از هر عملیات، دسترسی کاربر
  (مدیر بودن یا عضویت در تیم) رو چک می‌کنه.
- **دیتابیس**: Team و Project رابطهٔ یک‌به‌چند دارن (یک تیم می‌تونه چند پروژه داشته باشه)؛
  عضویت در تیم به‌صورت آرایهٔ رفرنس (`members`) نگه‌داری می‌شه، نه embedding — چون عضویت در
  اینجا مستقل از یک پروژهٔ خاصه و باید بین چند پروژهٔ همون تیم مشترک بمونه.
- **لایهٔ داده**: `lib/serialize.js` مستندهای خام Mongoose (`.lean()`) رو به شکل ثابتی
  (DTO) برای فرانت‌اند تبدیل می‌کنه، تا کامپوننت‌های React مستقل از جزئیات دیتابیس بمونن.
